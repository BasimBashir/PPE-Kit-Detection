# 10 — API and WebSocket contracts

**Status:** VERIFIED (backend integration tests + running dashboard)
**Implements:** FR-API-001..004, FR-UI-001..006, NFR-SEC-001/002 · **Modules:** `backend/app/api/`, `backend/app/schemas/`, `frontend/src/services/`
**Related ADRs:** ADR-009 (REST + WebSocket), ADR-012 (auth)

## Purpose and scope
Versioned REST API under `/api/v1` and one WebSocket `/ws/live` used by the React dashboard. OpenAPI is generated by
FastAPI at `/api/docs` (Swagger) and `/api/openapi.json`.

## Assumptions
Single site, local network, dashboard served by the same FastAPI process (same origin; no CORS needed in production).
Vite dev server proxies `/api` and `/ws` to `:8000`.

## Conventions
- JSON, `snake_case`, timestamps are **ISO-8601 UTC strings** (`2026-11-02T12:00:00.123Z`) except telemetry-derived
  numeric `*_age_s` / `*_fps` fields. Units are in field names (`_s`, `_ms`, `_bytes`, `_fps`).
- Errors (FR-API-004): any non-2xx returns
  `{"error": {"code": "not_found", "message": "Event not found", "details": null}, "request_id": "9f1c..."}`;
  codes: `bad_request`, `validation_error` (details = pydantic errors), `unauthorized`, `forbidden`, `not_found`,
  `conflict`, `rate_limited`, `unavailable`, `internal_error`.
- Pagination: `?limit=50&offset=0` (limit max 200) → `{"items": [...], "total": 123, "limit": 50, "offset": 0}`.
- Auth: `Authorization: Bearer <token>` (opaque, server-side session, 12 h). WebSocket: `/ws/live?token=<token>`.
  Roles: `viewer` (read), `operator` (+ acknowledge/resolve/feedback), `admin` (+ cameras/rules/zones/users/settings/system).
- Credentials are write-only: camera responses contain `credential_ref` (e.g. `"env:RTSP_READ"`) and
  `has_credentials: bool`, never usernames/passwords/resolved URIs.

## WebSocket `/ws/live`
Server → client (JSON text frames):
1. On connect (and every reconnect — FR-API-002 / spec 9 fresh state): `{"type":"snapshot","cameras":Camera[],"open_events":Event[],"metrics":MetricsSummary}`
2. `{"type":"camera_status","cameras":(CameraStatus & {camera_id})[]}` — 1 Hz
3. `{"type":"event_created","event":Event}` / `{"type":"event_updated","event":Event}` — via the outbox (`dashboard` channel)
4. `{"type":"metrics","metrics":MetricsSummary}` — every 5 s
5. `{"type":"worker","up":bool,"pid","run_id"}` — on change
6. `{"type":"ping","ts"}` every 15 s
Client → server:
- `{"type":"event_rendered","event_id","rendered_at":"ISO"}` — sent once per `event_created` after it is painted
  (via `requestAnimationFrame`); server sets `events.dashboard_rendered_at` (first only) and observes
  `ppe_event_to_dashboard_latency_seconds` (NFR-PERF-005). Same host clock: browser and server run on the demo machine.
- `{"type":"pong"}`

## Failure modes
- Worker down: camera statuses become `null` → UI shows "Pipeline worker down" and cameras as unknown/stale, never ONLINE.
- DB down: `/ready` 503, events list returns `unavailable`; live camera status keeps flowing from the worker.
- WS disconnect: client reconnects with exponential backoff (1→15 s) and replaces state from the next `snapshot`.

## Security / privacy
No credentials in any response; evidence only by event id through an authenticated route; no person identity fields exist.
Login rate limit 5/min/IP; argon2id password hashes; tokens stored as sha256 hashes.

## Performance implications
Camera wall polls `/snapshot` per visible camera at ≤ 2 Hz (preview JPEG ~30–60 KB); detail view polls `/frame` at
≤ 5 Hz. WebSocket carries only small JSON.
